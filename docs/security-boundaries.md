# MaatruMitra — Security, Privacy & Operational Boundaries

> **DOCUMENT STATUS**: Architecture & Governance Reference  
> **SCOPE**: Concept Demonstration & Prototype Baseline (Non-Production)

---

## 1. Prototype Boundary & Intended Use

MaatruMitra is an **administrative follow-up intelligence tool** designed for ASHA and ANM healthcare teams in Karnataka.

### Strict Negative Boundaries (What MaatruMitra Is NOT)
- **NOT a Diagnostic Engine**: It does not evaluate symptoms, determine clinical risk, calculate triage scores, or diagnose illnesses.
- **NOT a Prescription System**: It never recommends medications, dosage changes, or medical therapies.
- **NOT an Autonomous Escalation Tool**: It never sends unverified alerts to beneficiaries, families, or doctors.
- **NOT Connected to Live Health Registries**: It does not link with RCH (Reproductive and Child Health), e-Kavach, or ABDM registries.

Every follow-up draft generated by the system is purely an **administrative task proposal** that requires human confirmation by an authorized ANM before any action is logged.

## 2. Consent Model & Data Minimization

```
[Beneficiary Verbal/Physical Consent]
               │
               ▼
[Explicit Consent Flag (consent_given: true)] ──► [Voice Note Upload Permitted]
               │
               ▼
[Opaque Reference: BEN-DEMO-001] (No PII: No Name, No Aadhaar, No Phone)
```

1. **Explicit Consent Prerequisite**: The backend rejects voice note creation if `consent_given: true` is not explicitly declared.
2. **Pseudonymization & Opaque References**: The database never stores real patient names, national identity numbers (Aadhaar), phone numbers, or home addresses. Records reference opaque identifiers (e.g. `BEN-DEMO-001`).
3. **Data Retention Limits**: Each beneficiary reference includes a `data_retention_until` timestamp. In a production system, all associated audio and raw transcripts are automatically purged once retention expires.

## 3. Role-Based Access Control (RBAC) & Area Scoping

Access control is enforced at the database repository and route middleware layers:

| Role | Permitted Actions | Scoping Boundary |
|---|---|---|
| **ASHA Worker** | Record voice notes, edit transcripts, create drafts, acknowledge and complete tasks | **Creator-Only**: An ASHA can access only their own recorded notes and assigned tasks. |
| **ANM Reviewer** | View area review queue, confirm drafts, revise drafts, dismiss drafts | **Area-Scoped**: An ANM can view and confirm drafts only within their designated PHC area (`assigned_area_id`). |
| **PHC Admin** | Cross-area monitoring, system audit log viewing, development demo reset | **PHC Area / Facility**: Administrative oversight; reset actions are blocked in production. |

### Anti-Self-Assignment Rule
ANMs cannot assign tasks to themselves. When confirming or revising an administrative draft, the ANM must select an active, eligible ASHA worker within the draft's assigned area.

## 4. Permanently Disabled Messaging Architecture

To prevent inadvertent or automated messaging to beneficiaries:
- The `notification_outbox` database table contains a hard SQL constraint:
  ```sql
  CHECK (status = 'DISABLED')
  ```
- Any attempt by any service to insert an active notification (e.g. `QUEUED` or `SENT`) causes an immediate database exception.
- No external telecom, SMS gateway, or WhatsApp Business API integrations exist in this codebase.

## 5. Observability & Redacted Request Tracing

Every incoming HTTP request receives an `X-Request-Id` (e.g. `req_xxxxxxxxxxxx`).

### Logging Redaction Rules
Structured server logs record only metadata:
- HTTP Method (`GET`, `POST`)
- Normalized Path (without sensitive query parameters)
- Status Code (`200`, `403`, `409`)
- Execution Duration (`ms`)
- Authenticated Role (`ASHA_WORKER`, `ANM_REVIEWER`, `PHC_ADMIN`)

**Strictly Prohibited from Logs & Error Responses**:
- Raw audio storage paths and presigned URLs
- Kannada transcript text and revisions
- JWT access/refresh tokens and password hashes
- HTTP cookie headers
- Beneficiary reference aliases and clinical notes

All client error responses return sanitized messages with the matching `request_id` for administrative troubleshooting without leaking internal stack traces.

## 6. Development vs. Production Safety Barriers

| Capability | Development (`NODE_ENV=development`) | Production (`NODE_ENV=production`) |
|---|---|---|
| **Demo Reset Endpoint** (`POST /admin/demo-reset`) | Available to `PHC_ADMIN` | **Strictly Blocked** (`409 PolicyError DEV_ONLY`) |
| **Schema Migrations** | Auto-applied on dev startup | **Must be pre-applied** via migration script |
| **Content Security Policy (CSP)** | Relaxed for Vite HMR | **Strict Helmet CSP** headers enforced |
| **Audio File Storage** | Local directory (`./uploads`) | Dedicated object storage with encryption-at-rest |

## 7. Pilot Readiness & Governance Requirements

Before MaatruMitra can be evaluated in any live pilot with real field workers or beneficiaries, the following compliance milestones must be achieved:

1. **Ethics Committee Approval**: Review and clearance from an accredited Institutional Ethics Committee (IEC).
2. **Data Protection Impact Assessment (DPIA)**: Formal compliance audit under the India Digital Personal Data Protection (DPDP) Act 2023.
3. **Clinical Governance Review**: Alignment with Karnataka State Health & Family Welfare Department RMNCH+A standard operating procedures.
4. **Speech-to-Text Benchmark**: Dialect-specific accuracy certification for North and South Karnataka Kannada phonology.
5. **ABDM Sandbox Certification**: Official Ayushman Bharat Digital Mission (M1, M2, M3) health data integration certification.
6. **Infrastructure Security Audit**: Third-party CERT-In empaneled penetration testing and vulnerability assessment.
